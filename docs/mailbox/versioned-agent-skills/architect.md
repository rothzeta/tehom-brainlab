## Design and boundaries

Create the three directories named in the assignment, retaining the existing `ruach-handoff` instruction contract. Each skill carries its own scripts, concrete tests/fixtures, and any required package manifest and lockfile. There are no imports across skill directories, root runtime packages, experiment paths, repository-name checks, model defaults, or global installation requirements. A copied skill must run independently with Bun after its own documented frozen dependency install.

Keep each SKILL.md short: purpose, public commands, failure semantics, essential constraints, and links to relevant local references. Put adapter details in `ruach-herdr/references/adapters.md`, routing normalization in `references/routing.md`, and evaluation configuration in `ruach-harness-eval/references/config.md`. These files document real contracts, not duplicated manuals. Version the runtime/result interfaces with `schema_version: 1`; repository Git and skill-local package versions identify the implementation. Breaking interface changes require a new schema version.

`ruach-herdr` prepares and starts one named session. It does not send assignments, monitor task progress, coordinate workers, validate handoffs, run acceptance, or benchmark. `ruach-handoff` checks report syntax and references without executing checks or certifying truth. `ruach-harness-eval` evaluates supplied candidates; it does not create workers, implement tasks, integrate branches, or operate periodic watchers. Daily Coordinator instructions must not select/load the evaluator automatically.

## Routing contract and integration seam

Normalize repository data to a small internal `ResolvedWorker { role, roleFile, route?, kind, model, effort?, cwd, repo, provenance }`. Only `scripts/routing.ts` knows YAML shape; adapters consume normalized values. `--repo` selects the canonical repository root; absent it, infer from `git -C <cwd> rev-parse --show-toplevel`, which correctly identifies the requested worktree. Resolve relative CLI paths from invocation cwd. Use canonical roles under that selected root's `.agents/agents/`; cwd must exist, and its Git/worktree association must be recorded. Do not find a route by reading another worktree or Git's common-directory parent.

**Provisional minimal schema assumption, not verified against the concurrently authored schema:** three root YAML mappings with string identifiers. `models.yaml` has `models: { MODEL_ID: { kind: KIND, model: NATIVE_MODEL, efforts: [LEVEL, ...] } }`; `routing.yaml` has `routes: { ROUTE_ID: { model: MODEL_ID, effort?: LEVEL } }`; `roles.yaml` has `roles: { ROLE: { preferred_route: ROUTE_ID } }`. `efforts` may be empty for models without an effort contribution. Canonical role filenames follow role identifiers and need no copied YAML instruction body. No route inheritance, automatic fallback, or priority algorithm is assumed. These example field names are deliberately isolated and must be adapted to the committed schema; do not create or edit these YAML files in this work.

Validate YAML syntax, unique keys, types, every referenced model/route/role, known harness kinds, existing canonical role files, nonempty native model identifiers, and effort compatibility before generating files or splitting panes. Validate the complete reference graph, then the requested effective selection. Errors identify source file and key. Direct mode skips route files, but validates the role and native capabilities. The data declares permitted effort combinations; native documentation/help/catalog supplies a second capability check. Where remote account/model availability cannot be established read-only, disclose that limit; never claim entitlement or substitute a model.

Integration must confirm exactly: (1) committed YAML locations, version markers, mapping/list shapes and key names; (2) model-id versus native-id distinction and which object owns harness/provider/effort; (3) role preference and named-route selection semantics, any allowed overrides/inheritance/fallbacks; (4) declared effort vocabulary and model capability metadata; (5) canonical role-source paths and relative-path anchors; (6) unknown-key/reference validation rules; (7) existing root launcher's expected argv/JSON/exit contract and environment. Capture fixtures from that committed schema, with its revision, before enabling route-based `start`. A schema mismatch blocks routed starts, not direct-mode or independent skills.

The later root Python command performs only argument delegation: select the repository's versioned skill path and Bun executable, then pass `start`/`resolve`, role/route/cwd/name, and explicit native args as argv; forward stdout/stderr and exit status. It must not resolve routes, duplicate native flags, inject roles, create a second pane, or retry launches. Its implementation and YAML integration belong to the parent task.

## Handoff protocol and schema

Preserve statuses exactly: `complete`, `blocked`, `needs-decision`, `failed`. Completion means the assigned work is done, not that validation establishes acceptance. The seven required leading fields remain `task`, `status`, `outcome`, `artifacts`, `verification`, `discoveries`, `blockers`.

Use a bare YAML mapping at byte zero (allow BOM/CRLF), ending at the first unindented blank separator or EOF. No Markdown title before the mapping. Indented blank lines within a YAML block scalar do not terminate it. Parse one mapping; reject duplicate keys, malformed YAML, aliases/custom tags, extra YAML documents, scalar/list headers, and malformed types. This intentionally covers the existing P01 format without adding a Markdown scraping heuristic or rewriting history. Fenced/frontmatter alternatives are outside v1 unless a caller demonstrates a concrete need.

Structural JSON Schema: draft-07, required seven fields; nonempty string `task`/`outcome`; status enum; `artifacts`, `discoveries`, `blockers` arrays of strings (empty allowed); `verification` either literal `not-run` or an array (empty allowed) of strings or single-key mappings whose value is a string. That narrowly bounded mapping alternative preserves the actual P01 Implementer/Reviewer/delivery YAML: unquoted `- Check label: result` parses as a mapping. Reject numeric/null/nested/multiple-key verification entries; recommend quoted strings for new narratives. Optional `review` has the same neutral-string/list shape; absent review means not-run. Optional revision fields are nonempty strings. Permit additional fields for existing report metadata; `patternProperties` constrains every `*_revision`, and explicitly `source_baseline`, `destination_before`, and legacy `revision`, to the same revision-string type. Do not parse arbitrary SHA-looking prose, artifact strings, or branch-name list entries as mandatory revision fields. No semantic success inference, status-dependent requirement for passing checks, or automatic report conversion.

`handoff.schema.json` is the sole structural validator specification; execute it with Ajv with coercion/default insertion disabled. Separate Markdown/YAML extraction errors and contextual Git diagnostics from schema errors. JSON Schema can describe revision strings, but cannot express whether objects exist in an external repository: document that contextual check expressly, rather than falsely claiming a schema file alone proves revision existence. The validator accepts exactly the schema's structural values plus these stated parsing/context constraints; no hidden field validation rules or success defaults.

Resolve every supplied revision with Git `rev-parse --verify --end-of-options <ref>^{commit}` in the report's repository; accept hashes/refs that resolve to commits, output resolved full identities, and reject option injection, missing refs, and noncommit objects. No network fetch. Explicit `--repo` (anchored to invocation cwd) wins. Otherwise infer via Git from the report's containing directory, never caller cwd or a hard-coded root; detached report outside Git requires `--repo`. Worktrees use their own repository context, not a sibling main checkout. A report covering another repository uses explicit context; split multi-repository evidence into separately validated reports in v1.

`candidate_revision` is the identified candidate; `tested_revision` is the revision actually checked; `reviewed_revision` is the reviewed revision; `delivered_revision` is the existing delivery. Keep historical `independently_tested_revision`, `reused_evidence_revision`, and `source_baseline` meaningful and resolvable without equating them. No required equality, HEAD matching, ordering, or ancestry in the handoff validator. Evidence-only successors may legitimately differ; equivalence and ancestry belong to explicitly configured evaluation/review. A report never needs its own creating commit: commit the report, then supply the observed report-containing SHA in the terminal handoff.

Neutral template: `verification: not-run`, `review: not-run`, empty lists for artifacts/discoveries/blockers, and no revision placeholders or prefabricated success. Authors fill task/status/outcome and the report artifact before use. Mechanical diagnostics do not establish that listed artifacts exist, checks ran, review approved, or evidence is honest.

Historical boundary: the six P01 handoff/verification reports were parsed with PyYAML during this design audit. Their seven fields have the expected outer types; Implementer, Reviewer and delivery verification lists contain the single-key mappings accepted above. These reports are useful compatibility fixtures. Older Claude/Codex Architect injection reports, experiment assignments/results/observer-source and mailbox README start with headings and are narrative records. Explicitly passing those narratives fails with `header_missing`; never recursively validate all Markdown as if it were a handoff. Preserve their historical formats. Use sanitized fixtures for portable tests rather than importing repository-specific absolute paths/revisions.

Canonical files record baseline/candidate/worktree hashes and apply equality only when requested. Join acceptance and scope by supplied evidence task/run/candidate identities, never array position or hard-coded harness sets. Historical JSON is evidence to inspect, not silently treated as the v1 schema.
