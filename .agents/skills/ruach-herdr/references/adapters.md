## Configuration preservation and visibility

Codex app-server `config/read` is used rather than manually approximating precedence from user TOML. A matching existing daemon is an extra prerequisite to keep `resolve`/dry-run free of daemon bootstrap/storage initialization. Only relevant developer/skills fields are used in memory; raw response bodies are never logged. Instruction text goes into one native TOML argv override, preserving the default harness prompt. Existing `skills.config` entries are retained, including disabled unrelated skills. Worker workflow overrides cover native catalog paths, canonical paths and aliases, both SKILL.md and folder representations because installed catalogs and current docs use different representations. Developer text and skill config payloads are redacted in public argv.

Claude keeps normal user/project/native instructions and settings discovery. `--append-system-prompt-file` references the canonical role, while `--settings` merges a minimal overlay instead of copying user settings. Discovery scans repository, cwd ancestors, personal skills and accepted additional directories, using frontmatter names to recognize workflow aliases. Canonical technical skill directories are linked into private `.claude/skills` and exposed through `--add-dir`. Duplicate canonical names fail before temp creation. Worker launch fails when an enabled plugin's installation cannot be inspected or contains a workflow skill: native skillOverrides do not filter plugin skills. Workers also fail before mutation when local managed settings/skills, account-synced skills, or linked-worktree main-checkout fallback are detected; effective native visibility for those sources has not been verified. Existing nested project skill roots are scanned before launch so later file access cannot expose their workflow names. Legacy workflow commands fail as unverified. Skills newly added after launch remain outside this launch-time snapshot. Do not infer native catalog acceptance.

All temporary files remain private, reference canonical skill/role sources, and are never committed. Real Codex/Claude checks exercise resolution and effective argv preparation only. Fakes inspect generated settings and native argv; they do not emulate the entire native prompt or skill loader.

## Lifecycle and failure

Read-only preflight verifies executables, installed help, Herdr kind support, explicit caller context, caller layout and unique live name. Right split at caller width >=120, otherwise down. The new pane uses `--cwd`, `--no-focus`, and verified `--env` for the caller’s PATH, HOME and already-set CODEX_HOME/CLAUDE_CONFIG_DIR so executable/config resolution agrees with preflight. These values are forwarded unchanged; the skill never selects a replacement config home. No permission-policy default is injected. Help probes use `agent start --help`; they are distinct from the single mutating startup submission.

After preflight, only Claude needs private material: portable OS temp root or supplied existing directory, `ruach-herdr-` prefix, 0700 directory, 0600 settings file, canonical symlinks. Failure before split removes private material. Once split is attempted, any failure is uncertain: report phase, name, pane when known, retained temp directory and `submission_state: unknown`, exit 4. Never retry, close the pane automatically, or remove material a submitted process may need. Successful startup retains private material for caller cleanup after the session ends. No prompt, monitoring, watcher, scheduler, eval or benchmark command is issued.
