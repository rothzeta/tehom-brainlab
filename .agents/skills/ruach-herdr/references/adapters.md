## Configuration preservation and visibility

Codex app-server `config/read` is used rather than manually approximating precedence from user TOML. A matching existing daemon is an extra prerequisite to keep `resolve`/dry-run free of daemon bootstrap/storage initialization. Only relevant developer/skills fields are used in memory; raw response bodies are never logged. Instruction text goes into one native TOML argv override, preserving the default harness prompt. Existing `skills.config` entries are retained, including disabled unrelated skills. Worker workflow overrides cover native catalog paths, canonical paths and aliases, both SKILL.md and folder representations because installed catalogs and current docs use different representations. Developer text and skill config payloads are redacted in public argv.

Claude keeps normal user/project/native instructions and settings discovery. `--append-system-prompt-file` references the canonical role, while `--settings` merges a minimal overlay instead of copying user settings. Discovery scans repository, cwd ancestors, personal skills and accepted additional directories, using frontmatter names to recognize workflow aliases. Canonical technical skill directories are linked into private `.claude/skills` and exposed through `--add-dir`. Duplicate canonical names fail before temp creation. Account-synced caches, plugins, managed sources, legacy commands and linked-worktree fallback do not gate preparation. The launcher neither injects their bodies nor changes them. Existing nested project skill roots are scanned for targeted known-name suppression; account-synced caches are left to native discovery. Full catalog exclusion, including newly added entries after preparation, is unverified and not required by the role/instruction contract. Do not infer native catalog acceptance.

All temporary files remain private, reference canonical skill/role sources, and are never committed. Real Codex/Claude checks exercise resolution and effective argv preparation only. Fakes inspect generated settings and native argv; they do not emulate the entire native prompt or skill loader.

## Visibility limits and Codex reader investigation

The corrected contract requires only the Coordinator to load/execute workflow bodies, and prohibits launcher injection of workflow bodies into worker instructions. It does not require universal exclusion of workflow descriptions in native catalogs. Claude appends only the canonical role; known local workflow names receive the documented per-launch `skillOverrides` overlay. Coordinator overlays do not force disabled workflows on. Normal native customization discovery and its unrelated settings remain intact.

Installed Claude 2.1.289 has an account-synced cache. The [skills documentation](https://code.claude.com/docs/en/skills#override-skill-visibility-from-settings) excludes plugin skills from `skillOverrides`, and account inventories can change. Live account/plugin/managed/legacy catalogs and worktree fallback are therefore unverified visibility limits, not startup prohibitions. No `--bare`, `--safe-mode`, source restriction, slash-command disable, sync toggle or persistent cache movement is emitted. Fixture tests establish preparation and byte preservation, not live catalog acceptance.

Installed Codex 0.160.0 supports `app-server --listen stdio://`. The [official app-server contract](https://developers.openai.com/codex/app-server/) documents initialization and config/catalog reads independently from model turns. A short-lived isolated HOME/CODEX_HOME probe sent only initialize, initialized, config/read and skills/list. It returned the trusted project developer override, left pre-existing config bytes unchanged and exited 0, but created persistent state: state_5, goals_1, logs_2, memories_1 and queue_1 SQLite databases with WAL/SHM files, installation_id and system-skill files. These remained after exit; it also created .tmp plugin-lock and git HEAD files. The probe’s temporary tree was removed, without touching real user state or the existing daemon.

Those writes are not merely ephemeral runtime files. The [config reference](https://developers.openai.com/codex/config-reference/) documents `sqlite_home`, but redirecting one database path does not establish absence of the other initialization writes. Replacing the real config home would discard actual user layers; no such approximation is used. Installed debug help provides model/prompt tools and an app-server message sender, not a verified standalone effective-config reader. No suitable native reader satisfying the no-user-state-write constraint was verified. Keep the matching existing-daemon prerequisite; the skill never bootstraps a daemon or inspection subprocess. This is a bounded evidence-based limitation of the installed version, not a claim that future versions cannot provide a safe reader.

## Lifecycle and failure

Read-only preflight verifies executables, installed help, Herdr kind support, explicit caller context, caller layout and unique live name. Right split at caller width >=120, otherwise down. The new pane uses `--cwd`, `--no-focus`, and verified `--env` for the caller’s PATH, HOME and already-set CODEX_HOME/CLAUDE_CONFIG_DIR so executable/config resolution agrees with preflight. These values are forwarded unchanged; the skill never selects a replacement config home. No permission-policy default is injected. Help probes use `agent start --help`; they are distinct from the single mutating startup submission.

After preflight, only Claude needs private material: portable OS temp root or supplied existing directory, `ruach-herdr-` prefix, 0700 directory, 0600 settings file, canonical symlinks. Failure before split removes private material. Once split is attempted, any failure is uncertain: report phase, name, pane when known, retained temp directory and `submission_state: unknown`, exit 4. Never retry, close the pane automatically, or remove material a submitted process may need. Successful startup retains private material for caller cleanup after the session ends. No prompt, monitoring, watcher, scheduler, eval or benchmark command is issued.
